# 功能验收与回归

把“代码改完”转换为“用户目标已达成”。这个 skill 默认只检查和报告，不擅自继续扩大需求；发现失败时，输出可复现的问题并转给 app-diagnose 或 qa。

## 验收前读取

优先读取：

- 用户确认过的方案、PRD、问题描述或变更说明
- AGENTS.md 中的启动、构建和测试命令
- 本次改动涉及的代码、测试和配置

如果没有明确的目标行为，先补齐“期望表现”和“实际表现”，不要凭感觉判定通过。

## 检查顺序

### 1. 核心路径

按用户真实操作走一遍：进入页面、填写或选择输入、提交、查看结果、刷新或重新进入。记录每一步的预期和实际结果。

### 2. 边界和失败路径

至少检查一项空输入、非法输入、重复提交、权限不足、网络或外部依赖失败。涉及数据写入时，确认失败不会造成重复、丢失或半成功状态。

### 3. 现有行为回归

检查受影响页面、相关列表、导航、登录权限、数据展示和已有测试。不要为了“顺手”扩展到无关区域。

### 4. 界面任务

如果改动涉及 UI，再检查桌面和窄屏布局、键盘可操作性、焦点、错误提示、加载和空状态。不要只看静态截图。

### 5. 证据

运行项目中已有的最小相关命令。命令不存在就写“未发现”，不要编造成功。区分：已验证、未验证、无法验证。

## 输出格式

# 验收结果

## 结论
通过 / 有条件通过 / 不通过

## 已验证
- [行为]：通过，证据是...

## 未通过或阻塞
- [问题]：重现步骤...
- 期望：...
- 实际：...

## 未验证
- [项目或命令]：原因...

## 剩余风险
- [风险、影响、建议]

## 下一步
通过则结束；失败则转给 app-diagnose 或 qa。

“有条件通过”只能用于非阻塞风险已经明确、用户仍可完成核心任务的情况；核心路径失败、数据可能丢失或权限边界不清时必须“不通过”。

## 边界规则

- 不把编译成功、单元测试通过或页面能打开当作完整验收。
- 不为了让结果通过而修改验收标准。
- 不在没有用户授权时删除数据、调用生产接口或提交外部审批。
- 不把模拟数据、手工代办或测试环境结果写成生产能力。
