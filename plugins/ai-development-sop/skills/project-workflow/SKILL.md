# 项目开发流程路由

把一次对话放进正确的开发阶段，避免需求澄清、评估、实现、排错和验收互相跳过。这个 skill 负责判断“现在该做什么”和“什么时候可以进入下一步”，不替代具体的代码、设计或排错 skill。

## 先读取项目事实

开始前读取：

- AGENTS.md、README.md 和已有 docs/
- package.json、锁文件、构建和测试配置
- 相关源码、测试和当前 Git 状态（只读）

找不到的内容标记为“未知”，不要猜命令、技术栈或业务规则。没有 AGENTS.md 时，项目规则初始化应转给 agents-md-init。

## 先判断请求类型

| 用户表达 | 当前入口 | 下一步 |
|---|---|---|
| “我想做一个”“有个想法”“从 0 开始”但目标不清 | 新项目 | brainstorm |
| 给出 SOP，想判断能否系统化 | 流程评估 | sop-feasibility-review |
| 已有通用 SOP，想适配当前项目 | 流程整理 | sop-organizer |
| 需求已确认，想形成完整产品文档 | 产品定义 | to-prd |
| 新增、修改或迭代一个具体功能 | 变更实现 | 先写变更范围和验收条件，再进入实现 |
| “好像不对”“点了没反应”且信息不足 | 问题收集 | qa |
| bug 现象已能复述，准备定位原因 | 问题诊断 | app-diagnose |
| 重构、拆模块或维护性问题 | 代码结构 | zoom-out → improve-codebase-architecture 或 request-refactor-plan |
| 新页面或新界面 | 新设计 | impeccable（需要设计上下文）→ frontend-design |
| 已有页面不好看或响应式有问题 | 设计精修 | design-polish |
| 改完后“能不能用”“帮我验收” | 验收 | acceptance-check |

如果一个请求跨多个类型，先处理阻塞前置条件。例如“做一个审批系统但流程还没梳理”应先做可行性评估，不要直接进入页面开发。

## 阶段门

### 门 0：目标和责任

确认目标用户、要解决的问题、不能做的事，以及是否涉及支付、医疗、金融、身份、隐私、删除或代表用户对外操作。高风险事项先缩小范围并保留人工确认。

### 门 1：流程和需求

- 新想法必须经过 brainstorm，用户确认方案后才能写业务代码。
- 业务流程必须经过 sop-feasibility-review；结论为“暂缓”或“不建议系统化”时，不进入实现。
- 已确认但较大的产品需求可以使用 to-prd，不要用 PRD 代替用户确认。

### 门 2：变更范围

每次新增功能、修复问题或调整 UI，都先明确：

1. 现状和目标行为
2. 影响的用户、页面、数据或外部依赖
3. 明确不改的范围
4. 验收条件和失败时的恢复方式

范围不清时，回到 brainstorm、qa 或 app-diagnose；不要用猜测补齐。

### 门 3：实现

选择最窄的专项 skill：数据库变更用 database-model-docs，React Hooks 用 react-hook-best-practices，表格用 antd-table-guide，多语言用 i18n。通用代码修改遵循 karpathy-guidelines：小改动、真实依据、可验证结果。

### 门 4：验收

实现完成后必须进入 acceptance-check。验收通过才算完成；失败则生成一个可复现问题，回到 app-diagnose 或重新调整范围。不要用“代码改了”代替“用户目标已达成”。

## 每次路由的输出

先用大白话告诉用户：

当前阶段：...
本轮目标：...
下一步使用：...
现在需要你确认：...
本轮产物：...

如果用户只想问建议，直接给路由判断，不要擅自写文档或改代码。只有用户明确要执行时，才进入下一阶段。

## 完成检查

- 是否识别了当前阶段，而不是直接开始写代码？
- 是否检查了前置条件、风险和用户确认点？
- 是否避免同时调用多个作用重叠的 skill？
- 是否为实现定义了可观察的验收条件？
- 是否安排了实现后的验收和失败回流？
